# Review: Control plane Phase 4a (backups, schedules, API keys)

* Author: Claude (backend agent) · Reviewer: Codex gpt-5.6-terra (high, two passes) · Date: 2026-10-12 · Scope: eea6c13, 9241c35, 8798386

| # | Sev | Finding | Resolution |
|---|-----|---------|------------|
| B1 | **Blocker** | Rotation deletes the oldest good backup before the new one exists (limit 1 + failed backup = no backups) | Fixed: rotation is the last create step, after the new backup is completed (S3: uploaded + size-verified); it conditionally deletes the oldest unlocked completed backup (never the new one); a node without space fails with `QUOTA_EXCEEDED` and a clear message, nothing is pre-deleted. Test: `apps/control-plane/test/integration/review-phase4a.int.test.ts` "B1: rotates out the oldest backup only after the new one is complete; a failed backup keeps it" |
| H1 | High | Migration 0003 drops `scopes`/`revoked_at` → revoked or scoped legacy tokens could become active all-permission keys | Fixed: migration 0004 deletes (revokes) every `api_tokens` row created before 0003 (2026-10-12T18:45:06.507Z) or not in `bfk_<16 hex>` format. Test: "migration 0004 (H1, H4)" (runs the migration statement against seeded legacy rows) |
| H2 | High | `runNow` needs only `schedules.manage` but runs as the last editor → privilege delegation | Fixed: run-now requires every task's permission (403 naming the missing ones); a manual run snapshots the caller as executor (re-checked per task at run time). api.md text sent to the coordinator. Tests: "H2/H3: run-now needs every task's permission …", `schedules.int.test.ts` (bob 403) |
| H3 | High | Startup `recover()` fails runs that another replica is executing → duplicate execution | Fixed: runs carry `runner_id` + `lease_expires_at` (60 s, renewed every 20 s); `recover()` (startup and every tick) fails only runs whose lease expired; a lost lease fences the remaining tasks. Test: "H2/H3 …" (live foreign lease untouched, expired lease recovered) |
| H4 | High | S3 backups store only the key; restore/download/delete use the *current* storage settings (wrong bucket, possibly deleting an unrelated object) | Fixed: immutable `backups.storage_ref` per S3 backup (endpoint, region, bucket, prefix, forcePathStyle, accessKeyId, secretId); the secret is versioned (`backups.s3.secretAccessKey:<uuid>`, settings hold `secretId`) and an old version is kept while any backup references it; download/restore/delete/abort use the backup's reference; 0004 backfills settings + existing rows. Tests: "S3 storage references … keeps each backup's storage location …" (MinIO, two buckets), "migration 0004 (H1, H4)" |
| H5 | High | Lock check-then-delete race in rotation/deletion | Fixed: delete job, rotation and pruning delete the row first with `WHERE locked = false RETURNING` (a lock wins), then the data; the deleted row is kept in job state for retries. Test: "H5: deletion is a conditional delete of an unlocked row …" |
| H6 | High | Failed S3 uploads leave local archives behind (uncounted) → node disk exhaustion | Fixed: a failed/cancelled backup deletes its node-local archive (also for S3 backups that never finished uploading) and any open upload; failed rows are pruned by maintenance (newest 10 per server, ≤ 7 days, locked kept). Tests: "H6/M6/L3: failed backups are pruned …", S3 test (local archive gone after a failed upload) |
| H7 | High | Save-flush confirmation compares CP time with agent log timestamps (clock skew → stale match or timeout) | Fixed: waits compare console sequence numbers captured before each command (no timestamps); `save-off` must be acknowledged (`SAVE_OFF_TIMEOUT`, no archive); `isSaveFailure` fails at once (`SAVE_FAILED`). Tests: "H7: only a confirmation after save-all counts (console sequence, not timestamps; clock skew either way)", "H7: a save failure fails at once and an unconfirmed save-off stops the backup" |
| H8 | High | Successful backup restores `running` without checking the workload (crash during backup hidden) | Fixed: create/restore finalize settles a server still in `backing_up` from the real `workload.status`. Test: "H8: the state after a backup comes from the workload" |
| H9 | High | Finalize errors leave `active_operation` set (stranded lock) | Fixed: `withLockRelease` wraps the finalize hook of every server job and of backup create/restore (`state.end` in `finally`). Test: `test/unit/phase4.test.ts` "server job operation lock (H9)" |
| M1 | Med | `save-on` best-effort; no durable retry when the node disconnects | Fixed: `servers.save_on_pending` is set before `save-off` and cleared only when `save-on` is acknowledged; retried on node `sessionReady`, at startup and by maintenance (skipped during backup/restore, cleared when the workload is not running). Test: "M1: an unacknowledged save-on stays pending and is retried on reconnect and by maintenance" |
| M2 | Med | Multipart upload orphaned on presign failure/crash (upload id only in memory) | Fixed: upload id + key persisted before the agent upload; aborted on any failure (also when presigning fails after creation); `abortStaleUploads` at startup + maintenance aborts uploads of rows whose job is not running. Test: S3 test (a persisted orphaned MinIO multipart upload is aborted). The presign-failure abort path has no dedicated test |
| M3 | Med | Scheduler claims 20 per tick; bursts beyond the catch-up window silently lose runs | Fixed: a tick drains due schedules in batches of 20 (≤ 50 batches). Test: "M3/M6: one tick drains every due schedule in batches …" (45 due → 45 runs in one tick) |
| M4 | Med | Job waiting polls Postgres every 100 ms for hours; blocks shutdown | Fixed: job waits are woken by `job.updated` events with a backing-off poll (250 ms → 30 s) as safety net, 6 h cap, and end at once on scheduler stop. Test: "M4: waiting for a task's job ends at once when the scheduler stops" |
| M5 | Med | Schedule updates/deletes during a run: version skew, stuck `runningRunId` | Fixed: each run stores its definition (name, tasks, editor, onlyWhenOnline) when claimed and executes that snapshot; before each task the run checks `schedules.running_run_id` and its lease. Test: "M5: a run executes the definition it was claimed with; deleting the schedule fences the remaining tasks" |
| M6 | Med | Unbounded schedules per server and failed backups; unpaginated backup list | Fixed: max 50 schedules per server (409); failed-backup retention (H6); `GET /servers/:id/backups` paginated (`?limit` ≤ 500 default 100, `?cursor`, next page in the `x-next-cursor` header; contract CR: `Page<Backup>`). Tests: "M3/M6 …", "H6/M6/L3 …" |
| M7 | Med | AWS SDK checksum defaults vs agent raw part PUTs (strict S3 endpoints) | Fixed: S3 client with `requestChecksumCalculation`/`responseChecksumValidation: "WHEN_REQUIRED"`. Test: S3 test against MinIO (no checksum parameters in presigned part URLs; raw part PUTs accepted) |
| L1 | Low | API-key rate limit per process; invalid keys unthrottled | Fixed: per-key limit counted in fixed one-minute windows in `api_key_usage` (shared by replicas, pruned by maintenance); invalid keys limited to 30 per IP per 5 min (per process) before any lookup. Test: "L1: the per-key limit is counted in the database …" |
| L2 | Low | Console backfill size decided by the first request; system lines suppress backfill | Fixed: the backfill always fetches `BACKFILL_MAX_LINES` and control-plane `system` lines do not count as output. Test: "console backfill (L2)" |
| L3 | Low | Create-only users can create locked backups they cannot unlock | Fixed: creating a locked backup requires `servers.backups.delete`. Test: "H6/M6/L3 …" |
